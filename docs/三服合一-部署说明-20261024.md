## 二、部署步骤

### ⚠️ 步骤 0：升级前必做（老库）

**1. 备份数据库**

```bash
cp -a Data/gateway.db Data/gateway.db.bak-$(date +%Y%m%d-%H%M%S)
```

**2. accounts 表缺的列会自动补齐，不需要手工 SQL**

老库的 `accounts` 表缺后来新增的 8 个列（`device_secret_last_rotated` /
`s5a9_digest` / `last_login_at` / `last_login_ip` / `failed_login_count` /
`lockout_until` / `updated_at` / `last_heartbeat`）。
`EnsureInitialized` 会用 `ALTER TABLE ADD COLUMN` 自动补
（`ensureAccountColumnsUpgraded`，先 `PRAGMA table_info` 查再补，幂等）。

> ★ 为什么必须自动补而不是靠 `CREATE TABLE IF NOT EXISTS`：
> 那条语句对**已存在**的表是 no-op，不会加列。缺列时后面的
> `CREATE INDEX idx_accounts_last_heartbeat ON accounts(last_heartbeat)`
> 直接失败 → 整个初始化中断 → **网关启动失败**。
> 本地测试每次建全新库，所以这个坑只在真升级时暴露。
> 测试 `TestUpgradeFromLegacyAddsInviteTable` 用旧 schema 的库锁死这条路径。

**3. 先生成邀请码，再放玩家进来**

`Register.RequireInvite` 默认开启，升级后如果后台一个码都没有，**没人能注册**。

```bash
curl -X POST http://127.0.0.1:8443/api/admin/invite/generate \
  -H "X-Auth-Key: <AuthKey>" -H "Content-Type: application/json" \
  -d '{"count":20,"note":"首批","expires_in_hours":0}'
```

**4. 升级后验证**

```bash
systemctl status s4a21-gateway          # 起没起来
curl -s http://127.0.0.1:8080/api/health
sqlite3 Data/gateway.db "SELECT COUNT(*) FROM invite_codes"   # 邀请码表在不在
sqlite3 Data/gateway.db "SELECT m_id, name FROM accounts LIMIT 5"  # 老账号在不在
```

### 步骤 1：网关启用签名（每台网关各做一次）
在 `appsettings.json` 加（**已默认加上**）：

```json
"Signing": {
  "PrivateKeyPath": "./signing.key",
  "KeyExpirySeconds": 300
}
```

启动网关，日志会出现：

```
[Signing] 服清单签名已启用，公钥=3f8a1c...（128 个 hex 字符）
```

**首次启动会自动生成 `signing.key`（0600 权限）。这个文件不能删、不能换** ——
登录器 exe 里编译的公钥与它绑定，换了私钥等于全部旧登录器验签失败。

> 如果 `PrivateKeyPath` 留空：清单仍会下发，但 `signature` 为空。登录器按"未签名"
> 处理（降级模式，仅靠 TLS pin 保护）。**生产环境必须配。**

### 步骤 1.5：主网关配从网关列表（只有主网关要配）

```json
"Signing": {
  "PrivateKeyPath": "./signing.key",
  "KeyExpirySeconds": 300,
  "Peers": [
    {
      "Name": "s5a3-slave",
      "InternalUrl": "http://10.0.0.2:18080",
      "InternalKey": "<那台从网关自己的 Admin.InternalKey>"
    }
  ]
}
```

配了之后，**上传登录器 exe 或回退版本会主动推送到各从网关**，发版从
“等 300s 轮询”变成秒级生效。日志：

```
[PeerSync] 已配置 1 台从网关，上传登录器版本后会主动推送
[PeerSync] 已推送登录器版本到 s5a3-slave（v2.5.12 rev 42）
```

要点：

- `InternalUrl` 是**那台从网关自己的** internal 地址，不是主网关的
- `InternalKey` = 那台网关的 `Admin.InternalKey`（各台可能不同）
- 从网关**不配** `Peers`（它们只往外连）
- 推送失败不影响上传成功 —— 轮询兜底还在，日志会记
  `推送登录器版本到 xxx 失败（轮询兜底）`

### 步骤 2：把公钥编译进登录器

把上一步日志里的公钥粘贴到 `Launcher-WPF/LauncherConfig.cs` 的 `BuildDefaults`：

```csharp
internal const string SigningPublicKey = "3f8a1c...";  // ← 粘贴网关日志里的公钥
```

**三台网关用同一把私钥**（把主网关生成的 `signing.key` 拷到其余两台），
否则登录器连不同网关会拿到不同公钥，验签必然失败。

> 或者：每台网关各一把密钥，登录器按 bootstrap 地址区分公钥。
> 当前实现是"单公钥"设计（简单、够用）。要支持多密钥需要改
> `ServerListVerifier.Verify` 的公钥校验逻辑。

#### ★ 为什么清单里多了一个 `servers_json` 字段

这是本次改造最容易踩的坑，单独说明：

```
GET /api/launcher/servers 响应：
{
  "servers":      [ ... ],          ← 给人看的（curl / 调试）
  "servers_json": "[{...},{...}]",  ← ★ 签名覆盖的就是这个字符串的 UTF-8 字节
  "signature":    "abcdef...",
  "public_key":   "...",
  ...
}
```

**不能**让登录器"把 servers 反序列化再重新序列化"来验签，因为：

| | Go 侧 | C# 侧 |
|---|---|---|
| 键顺序 | `CanonicalJSON` 按 **key 字典序**（`auth_port` 在前） | `JsonSerializer` 按 **类属性定义序**（`id` 在前） |
| 空字段 | `omitempty` **省略** | 默认**输出空串** |
| nil 切片 | 输出 `null` | 输出 `[]` |

两端各自重序列化必然得到不同字节，验签**永远失败**。

解法：网关把自己生成的规范字节原样放进 `servers_json` 下发，
登录器对这段字符串的字节验签 —— 签的和验的是同一段字节，跨语言零风险。
（与 JWT 的 payload 处理同一思路。）

**这条链路的证据**是 `_work/ServerListSigTest`（C# 验证工程）：

```bash
# 1. Go 侧生成 fixture
cd Gateway-GO && go test ./pkg/httprouter -run TestEmitCrossLangFixture -v

# 2. C# 侧读取 fixture 验签（28 项断言）
cd _work/ServerListSigTest && dotnet run
# → 期望输出 "=== 全部通过 ==="，退出码 0
```

`fixture` 落在 `Gateway-GO/pkg/httprouter/testdata/crosslang/`。
**以后任何一端改了序列化方式，这个验证工程会立刻变红** —— 它是回归资产，
不是一次性脚手架。

### 步骤 3：配置服清单

每个 `GameServers[]` 条目可选配这些字段（**全部可省略，省略时从全局配置推导**）：

| 字段 | 省略时的行为 |
|---|---|
| `ListHost` | 用 `PublicIP` |
| `ListAuthPort` | 用 `Gateway.TcpPort` |
| `ListHttpPort` | 用 `Gateway.HttpPort` |
| `ListTls` | 用 `Tls.Enabled` |
| `ListPin` | 空（登录器用编译期 `PinnedFingerprint`） |
| `ListCaps` | **nil** → 按 Protocol 默认；**`[]`** → 显式全关 |
| `ListMinLauncherVer` | 用 `Launcher.MinVersion` |
| `ListHidden` | `false`（出现在清单里） |

`ListCaps` 可选值：`policy` / `pvf` / `plugins` / `integrity` / `kernel`。

协议默认值：

| 协议 | 默认 caps |
|---|---|
| `s4a21` | `policy, pvf, plugins, integrity, kernel`（全开） |
| `s5a95` | `policy`（只留策略） |
| `s5a3` | `[]`（五项全关） |

**这是本次改造最实用的一个开关**：以前 S5A3 五项全关是写死在代码里的，
现在运营在配置里写 `"ListCaps": ["policy", "integrity"]` 就能逐项打开。

### 步骤 3.5：本地 `Games[].Id` 必须与网关 `GameServers[].Id` 对齐

登录器按 `Id` 把"本地游戏档（决定客户端目录/exe/PVF）"与"网关清单条目（决定端点）"配对。

- `Games[].Id` 在清单里找不到 → 该服标为「不可用」，点登录会被前置拦截并提示切换
  （不回退到别的服 —— 否则玩家以为在登 X 服实际连到 Y 服）
- 两边 `Id` 大小写不敏感匹配，但**建议全小写**（网关侧 `Id` 只允许 `[a-z0-9-]`）

### 步骤 4：登录器 bootstrap 配置

`LauncherConfig.cs` 的 `BuildDefaults`：

```csharp
internal static readonly string[] BootstrapHosts =
{
    "1.1.1.1",   // 网关 A（主）
    "2.2.2.2",   // 网关 B
    "3.3.3.3",   // 网关 C
};
internal const int BootstrapHttpPort = 8080;
internal static readonly bool BootstrapTls = BuildDefaults.TlsEnabled;
```

**现在支持形态 A 部署**（评估文档第二章推荐形态）：三台机器各跑各的网关，
每个只配自己那条 `GameServers`，登录器把三个 bootstrap 的清单**合并**后展示。

合并规则：
- 按服 `Id` 去重，**先到先得**（`BootstrapHosts` 的顺序即优先级）
- 重复的 `Id` 会写进 `crash.log` 的 `server_list_id_conflict` 事件
  （两台网关配了同一个 `Id` 是运营错误，不该静默）
- 有效期取各源最大值（任一份还能用就不算过期）
- **任一台可达就能用**（部分源失败只记 `server_list_partial`，不阻断）

> ⚠️ `BootstrapHttpPort` 是**所有 bootstrap 共用的端口**。三台网关的 `Gateway.HttpPort`
> 必须一致（通常都是 8080），否则登录器连不上其中几台。
> 若各服端口不同，需要把这个常量改成 per-host 配置 —— 当前没做。

> ⚠️ 三台网关必须用**同一把 `signing.key`**，否则登录器只认其中一台的签名
> （单公钥设计，见步骤 2）。

### 步骤 5：网关间同步（可选，P0-4/P0-5）

**从网关需要配这三项**（主网关不用配）：

```json
"Signing": {
  "PrivateKeyPath": "./signing.key",
  "PeerBaseUrl": "http://<主网关公网或内网>:8080",
  "PeerInternalUrl": "http://<主网关内网>:18080",
  "PeerInternalKey": "<主网关的 Admin.InternalKey>"
}
```

| 字段 | 用途 |
|---|---|
| `PeerBaseUrl` | 拉登录器 exe（走公开端口，复用既有 ETag/限流） |
| `PeerInternalUrl` | 拉账号事件 / 版本元数据（走内部端口） |
| `PeerInternalKey` | 访问主网关内部 API 的密钥（= 主网关的 `Admin.InternalKey`） |

> ⚠️ 主网关的 `Gateway.InternalListenAddress` 默认是 `127.0.0.1`，跨机同步
> 必须改成内网地址（如 `10.0.0.9`），否则从网关连不上。

**账号事件同步 + 登录器版本同步（定时拉取，已自动运行）**：

从网关配了 `PeerInternalUrl` 后，`PeerSyncService` 会自动起两个定时器：

| 定时器 | 默认间隔 | 行为 |
|---|---|---|
| 账号事件 | 60s | `GET /internal/account/events?since=<水位>` → 应用全局封禁/解封 → 推进水位 |
| 登录器版本 | 300s | `GET /internal/launcher/sync?since=<本地最大 rev>` → 有新版就拉 exe |

可调：
```json
"Signing": {
  "PeerAccountSyncSeconds": 60,
  "PeerLauncherSyncSeconds": 300
}
```

启动日志会打印：
```
[PeerSync] 已启动：peer=http://10.0.0.1:18080 账号事件间隔=60s 登录器版本间隔=300s
```

未配 `PeerInternalUrl` 时打印（主网关的正常形态）：
```
[PeerSync] 未配置 Signing.PeerInternalUrl，本机不参与网关间同步（主网关的正常形态）
```

**推送（可选，秒级，比轮询快）**：

主网关上传新版后可以主动推：

```bash
curl -X POST http://<从网关>:18080/internal/launcher/push \
  -H "X-Internal-Key: <从网关的 InternalKey>" \
  -d '{"hash":"<64位大写hex>","version":"2.5.12","size":134217728,"revision":7}'
```

从网关收到后：
1. 已有同 hash → `{"ok":true,"skipped":true}`（幂等）
2. 没有 → 异步 `GET {PeerBaseUrl}/api/launcher/update/exe` 拉全量
3. 校验 SHA-256 必须等于 `hash`（**不匹配直接丢弃**）
4. 交给 `ReplaceLauncher` 完成入史 + 替换 + 清 delta
5. 把序号对齐到推送的 `revision`

未配 `PeerBaseUrl` 时返回 **501**（不假装成功）—— 主网关不需要配这一项。

> 推送不是必须的：300s 的定时轮询会兜住。推送只是让"发版到全服生效"从 5 分钟缩到几秒。

**账号凭据反查（登录兜底，自动运行）**：

从网关本地查不到账号时，自动向主网关反查凭据：

```
GET http://<主网关>:18080/internal/account/credential?name=<账号>
Header: X-Internal-Key: <主网关的 InternalKey>
→ {"ok":true,"exists":true,"pwd_hash":"...","salt":"...","m_id":"..."}
```

拿到后从网关会：
1. 用同一套算法在**本地**验密（不信任"主网关说对了"）
2. 验过 → 懒建本地副本（凭据用主网关的，`m_id` **本地分配**）→ 后续登录走本地路径
3. 验不过 / 超时（300ms）/ 主网关不可达 → 按原有逻辑报"账号不存在"

**这样"在主网关注册的号，立刻能在从网关登"**（评估文档 5.4 的目标）。

> ⚠️ 反查的 300ms 是硬超时：主网关慢不该把玩家卡住。
>   超时降级为"查不到"，失败方向保守（宁可让玩家重试，也不能误判账号被删）。

## 三、封号 scope 怎么用

后台封禁接口 `POST /api/admin/ban` 新增可选字段 `scope`：

```json
{"account": "badguy", "reason": "外挂", "scope": "global"}
```

| scope | 语义 |
|---|---|
| `global`（缺省） | 三服同时封（随账号事件同步广播） |
| `s4a21` / `s5a3` / `s5a95` | 只封该服（留在本服网关，不同步） |

封禁列表 `GET /api/admin/bans` 的每行新增 `scope` 字段。

登录校验：`scope='global' OR scope='<本服 id>'` 命中即拒。
**老数据（scope 为空）视为 global**，迁移不会让存量封禁失效。

## 五、风险与已知限制

| # | 风险/限制 | 现状 | 处置 |
|---|---|---|---|
| 1 | `BootstrapHttpPort` 是三台共用的常量 | 各网关 `HttpPort` 必须一致 | 若不一致需改成 per-host 配置（未做） |
| 2 | 自更新"主网关主动推"需手动触发 | 推送接收端 + 300s 轮询都在，但"上传后自动推"没做 | 靠轮询兜住；要秒级就手动 curl |
| 3 | 三台网关必须共用同一把 `signing.key` | 单公钥设计 | 拷密钥文件；或改多公钥校验 |

| 6 | 密码哈希不可全量跨服同步 | S4A21 MD5 / S5A3 bcrypt 硬约束 | 改为**按需反查**（登录时 300ms），不做全量同步 |
| 7 | 反查懒建时两服 `m_id` 撞号 | **本地分配新 m_id**，不沿用主网关的 | 已覆盖（撞号自动避开；沿用会串角色） |
| 8 | 反查可能变成"知道账号名就能建号" | ★ 本地必须自己验密通过才建号 | 已覆盖（`TestLazyCreateRejectedOnWrongPassword`） |
| 9 | 跨语言序列化差异导致验签失败 | 已用 `servers_json` 承载签名原文 | 已覆盖；`_work/ServerListSigTest` 是回归防线 |
| 10 | 反查增加登录延迟 | 300ms 硬超时，且只在"本地查不到"时触发 | 已覆盖；正常登录不走这条路径 |
| 11 | 清单能要求 tls=false（私钥泄露时可强制降级明文） | **产线构建拒绝**：清单只能加严不能放松 | 已覆盖（`BuildDefaults.IsProduction` 下 tls=false 的服被标为不可用 + 记 `server_list_tls_downgrade_rejected`） |
| 12 | Web 注册被脚本刷号 | IP 限流 + `RegisterLimit` + 4 KiB body 上限 | 已覆盖；但**无验证码**，高强度刷号需在反代加 WAF/限流 |
| 13 | Web 注册在反向代理后 IP 不准 | `clientIPOf` 取 `RemoteAddr`，不信任 `X-Forwarded-For` | 需在代理层处理（见 Web 注册页章节） |
| 14 | 邀请码泄漏后被滥用 | 一码一用（原子消耗）+ 可作废 + 可设有效期 | 已覆盖；泄漏后运营作废该码即可 |
| 15 | 邀请码消耗了但建号失败 | 码被标记已用，无法回退 | 刻意的取舍（防"试码"）；运营在后台看到记录后可补发 |

## 五之二、实施中发现并修掉的 bug（2026-10-24 第三～八轮）

这些都不是"计划内功能"，而是实施/验证过程中抓到的真问题。
共同特征是**单测全绿而线上坏着** —— 因为测试每次建全新环境，
走不到"旧 schema / 偶发时序 / 跨服组合"那些路。记录在这里，避免以后重新引入。

### bug 1：PVF 增量从错误的网关下载

`Security/PvfDelta.cs` 的 `ResolveUrl` 用的是编译期 `GatewayHost`，
而 `delta.Url` 是**选中服**的网关下发的。

后果：玩家选 S5A3 服，PVF 增量包却从 S4A21 的网关拉 —— 各服 `Script.pvf`
内容不同，产物整文件 SHA-256 必然不匹配 → 每次都增量失败 → 回退到
"校验失败 → 阻止启动" → 玩家进不去游戏。

修复：改走 `LauncherConfig.HttpBaseUrl`（按选中服解析）。

### bug 2：自更新的清单与 exe 来自不同网关

`LauncherSelfUpdate.CheckAsync` 用 `cfg.HttpBaseUrl`（选中服）拉清单，
但 `ResolveUrl`（下载 exe）用编译期 `GatewayHost`（主网关）。

后果：清单说"A 版、hash=X"，下载到的却是 B 版 exe → hash 校验失败 →
玩家每次都被要求更新却永远更新不完。

修复：两处统一走 `BootstrapBaseUrl()`（= 主网关）。**自更新刻意走主网关**
而不是选中服 —— exe 全局唯一、主网关是版本权威、检查可能早于选服。
这与 PVF 增量（必须按服）是相反的选择，两处注释都写明了原因。

### bug 3：选中服不在清单里时静默换服

`UpdateActiveServerEntry` 原先 `entry ??= manifest.Servers[0]`。

后果：玩家选了"本地有客户端但网关清单没有"的服（运营下线 / 该服网关没配进
`BootstrapHosts`），端点被静默换成清单第一个服 —— 玩家以为在登 X 服实际连到 Y 服，
用 X 的客户端连 Y 服，表现为"登录失败但日志里一切正常"。

修复：找不到就设 `ActiveServerEntry = null`（端点回退编译期）+ 记
`server_list_active_missing`；下拉框把该服标为「不可用」并给 ToolTip；
点登录时前置拦截并提示"请在下方切换到其它服务器"。

> 清单没拉到（`_serverList == null`）时**不拦** —— 首次运行断网仍应有机会登主服（fail-open）。

### bug 4：老库升级时网关启动失败（第七轮，2026-10-24）

**这是四个里最严重的一个**：另外三个只是"某些玩家登不进"，这个会让**网关起不来**。
`EnsureInitialized` 里的 `CREATE TABLE IF NOT EXISTS accounts (...)` 对**已存在**的
表是 no-op，不会补后来新增的列。于是紧接着的

```sql
CREATE INDEX IF NOT EXISTS idx_accounts_last_heartbeat ON accounts(last_heartbeat);
```

在旧库上直接报 `no such column: last_heartbeat`，整个初始化返回错误，网关启动中断。

**为什么单测没发现**：测试每次都建全新库（schema 一定是最新的），
只有真升级才会走到"旧 schema + 新代码"这条路。

修复：`ensureAccountColumnsUpgraded()` —— 在 `EnsureInitialized` 最前面用
`PRAGMA table_info(accounts)` 查现有列，对缺的列逐个
`ALTER TABLE accounts ADD COLUMN`。幂等（先查再补），重复调用安全。

回归防线：`pkg/database/upgrade_invite_test.go` 用**手工搭的旧 schema 库**
（只含 accounts / register_logs 两张老表 + 一条存量账号）跑升级，断言：
- 新表（`invite_codes` / `account_events` / `account_sync_state`）都建出来
- 新表**真的能读写**（不只是建出来）
- 存量账号不丢
- 重复 `EnsureInitialized` 幂等

> ⚠️ **以后给 accounts 加列必须同步 `accountColumnsUpgraded`** ——
> 漏了就会在升级时报 no such column。

### bug 5：RST 丢掉 PROXY 头，后端拿到 127.0.0.1（第八轮，2026-10-24）

抓它的过程：跑全量测试时 `pkg/proxy` 偶发失败（约 5%）。
第一反应不是"重跑试试"，而是**先把测试的诊断信息改到能分清故障类型** ——
原来假后端只回一个 `[]byte`，"Accept 失败"和"连上但读到 0 字节"
都被 `%q` 打成 `""`。分开之后立刻看到：

```
后端收到 0 字节（ReadErr=wsarecv: An existing connection was forcibly closed）
```

= **RST**。

**根因**：游戏口是**服务端先说话**协议，后端一收到 PROXY 头就主动下发
greeting。而拒绝路径（首包准入失败）上，greeting 可能已经到达网关、
躺在 backend 的**接收缓冲区里没人读**（downlink 协程刚起，未必已被调度）。
此时 `backend.Close()` 带着未读数据关闭 ⇒ 系统发 **RST** 而不是 FIN ⇒
**RST 会丢弃发送缓冲区里尚未 ACK 的数据**，也就是刚写进去的 PROXY 头。

**线上后果**（后端拿 127.0.0.1 当客户端地址）：

- PK 场 UDP 绑定校验失败
- 组队/副本下发给队友的 P2P 端点错
- 账号最后登录 IP 记成 127.0.0.1

**修复**：`closeBackendAfterReject(backend, downlinkDone)` ——
给 backend 一个 200ms 短读超时，让 downlink 协程醒来并把已到达的数据读走
（它本来就要转发 greeting），等它退出后再 `Close()`。此时接收缓冲区已空，
系统正常发 FIN，PROXY 头必然送达。三个拒绝点都改用它：

- 准入不通过
- 凭证准入时账号并发达上限
- 回退白名单时单 IP 并发达上限

**验证**：`TestRejectedGameConnNeverReachesBackend` 从 5% 失败降到
`-count=50` **0 失败**。

> **通则**：往一个连接写完之后要立刻关掉它**之前**，先确认接收缓冲区已读干 ——
> 否则可能触发 RST，把你刚写的数据一起丢掉。Linux 与 Windows 都有此行为。

### 注册：只在主网关，一次注册三服通用（2026-10-24 第四轮）

**产品决策**：注册入口唯一 —— 登录器保留注册按钮，但请求**固定发主网关**，
从网关直接拒绝注册请求。这样就不需要"从网关注册的号反向同步到主网关"
（那条路要明文密码跨服传，代价太大）。

#### 完整链路

```
玩家在登录器点"注册"
  ↓ 登录器固定连主网关（BootstrapHosts[0]），上报 账号 + MD5 + 明文
主网关 handleRegister
  ↓ ① 建"平台账号"（网关 accounts 表，MD5）
  ↓ ② 遍历 GameServers 里所有启用的 S5A3 服，用**明文密码**调它们的
  ↓    /api/account/register 建号
返回"注册成功"（或"注册成功（s5a3 服建号未完成…）"）
```

之后玩家在任意服登录：

| 服 | 登录路径 | 为什么能登 |
|---|---|---|
| S4A21 / S5A95 | 网关 accounts 表 | 平台账号就在主网关，本服没有就走**反查懒建**（300ms） |
| S5A3 | S5A3 服务端 MySQL | 注册时已经把明文转发过去建号了 |

#### 关键点：为什么主网关要转发给 S5A3

S5A3 的账号在它自己的服务端 MySQL（bcrypt），网关的 accounts 表推不过去。
但**注册时登录器手里有明文密码**，主网关可以用它调 S5A3 的
`/api/account/register` 建号 —— 这就是"注册一次 S5A3 也能登"的实现方式。

> ⚠️ **前提**：主网关的 `GameServers` 必须包含 `s5a3` 条目，且
> `AccountApiUrl` 从主网关**可达**（跨机时是内网地址）。
> 否则注册时找不到 S5A3 服，不会转发 —— 日志会有
> `注册未转发 S5A3（登录器未上报明文密码，可能是老版本）` 或干脆没有转发记录。

#### 从网关拒绝注册

判定依据：`Signing.PeerInternalUrl` 非空 = 从网关。

即使玩家绕过登录器直接调从网关的注册接口，也会被拒：
```
请在主网关注册账号（本服不提供注册入口）
```

这是"注册入口唯一"的技术保证 —— 不会产生"只在 B 服有的号"。

#### Web 注册页（可选兜底）

主网关提供网页注册，适合"登录器连不上主网关"或"手机/平板"场景：

```
http://<主网关>:8080/api/register
```

- `GET` 返回注册表单页
- `POST` 收 JSON `{"account":"...","password":"..."}`（**明文**，MD5 由网关算）

**为什么挂在 `/api/register` 而不是 `/register`**：`usePublicOnlyMiddleware`
会把所有非 `/api` 路径 404（玩家端口刻意不暴露页面）。想放根路径就得放宽那个
中间件，而它的存在是刻意的安全边界。

从网关访问该地址会看到"请在主网关注册"说明页（自动带上 `PeerBaseUrl` 拼出的链接）。

安全措施：

| 项 | 做法 |
|---|---|
| 从网关拒绝 | GET 返回说明页、POST 返回 403 |
| IP 限流 | 走 `httpRateLimitMiddleware` + `RegisterLimit`（Web 无机器码，只按 IP 判） |
| body 上限 | 4 KiB（正常请求 ~100 字节） |
| CSRF | 检查 `Origin` 与 `Host` 同源；无 `Origin` 的放行（非浏览器客户端） |
| 防点击劫持 | `X-Frame-Options: DENY` |
| 密码处理 | 只在内存中传给 `RegisterPlatform`，不写日志、不回显、不进 URL |

> ⚠️ 与登录器注册**共用同一份实现**（`service.AccountService.RegisterPlatform`），
> 所以"Web 能注册但登录器注册失败"这种漂移不可能发生。
> 两个入口都走同样的限额、同样的 S5A3 转发。

> ⚠️ 网关若在反向代理后面，`clientIPOf` 取的是 `RemoteAddr`（不信任
> `X-Forwarded-For`，因为它可被伪造用来绕限额）。这种部署需要在代理层
> 做 IP 白名单或改造成显式信任代理。

#### 配置

```json
"Register": {
  "PlatformOnly": true,   // 默认 true；配 false 回退到改造前的按服分流行为
  "RequireInvite": true   // 默认 true；配 false 关闭邀请码（回到自由注册 + IP 限额）
}
```

`PlatformOnly=false` 时恢复旧行为：选中 S5A3 服时注册只建 S5A3 账号（不建平台账号）。
保留这个开关是为了紧急回滚。

## 注册邀请码（2026-10-24 第六轮）

**产品需求**：有邀请码才能注册。管理后台生成，登录器和 Web 注册都要填。

### 完整链路

```
运营在后台「邀请码」页生成一批码
  ↓
玩家在登录器 / Web 注册页填写 账号 + 密码 + 确认密码 + 邀请码
  ↓
主网关 RegisterPlatform
  ① ★ 校验并**原子消耗**邀请码（在限额之前，见下）
  ② 建平台账号（MD5）
  ③ 转发明文给所有启用的 S5A3 服
  ↓
注册成功（码已被标记为这个账号所用）
```

### ★ 为什么邀请码校验要放在最前面

```go
if s.requireInvite() { ... 消耗码 ... }   // ①
RegisterWithLimit(...)                     // ② 限额判定 + 建号
RegisterS5A3(...)                          // ③
```

两个原因：

1. **没邀请码的人不该占限额名额**。IP 限额是"同一 IP 每天最多注册 N 个"，
   如果先扣限额再拒邀请码，攻击者用无效码就能把某个 IP 的限额耗光，
   误伤同网段的正常玩家。
2. 顺序反过来会让"邀请码是否正确"与"是否超限额"纠缠在一起，文案说不清。

⚠️ **代价**：邀请码消耗了但后续建号失败（重名/限额/库错）时，码就废了。
这是刻意的取舍 —— 宁可让运营补发一个码，也不给"用无效请求试码"留窗口。

### 一码一用（并发安全）

`ConsumeInvite` 用一条 SQL 同时完成"校验未用/未作废/未过期"和"标记已用"：

```sql
UPDATE invite_codes SET used_by = ?, used_at = ?
 WHERE code = ? AND used_by = '' AND disabled = 0
   AND (expires_at = 0 OR expires_at >= ?)
```

靠 `RowsAffected == 1` 判定成败，**不是"先 SELECT 再 UPDATE"** ——
那中间有窗口，两个并发请求会同时通过。

测试 `TestConsumeInviteConcurrent` 用 20 个 goroutine 同时抢同一个码，
断言成功次数恰好为 1。这是邀请码的安全核心：漏了它，一个码被发到群里
就等于无限次注册。

### 归一化：玩家不该为格式发愁

服务端 `NormalizeInviteCode` 会去掉空格/制表符/连字符/下划线/点/**不换行空格**，
并转大写。所以这些输入都是同一个码：

```
K7M2P9QX    k7m2p9qx    K7M2-P9QX    " k7m2 p9qx "    K7M2_P9QX    K7M2.P9QX
```

不这么做的话，"码明明是错的但提示有效"之外的**主要客服问题**就会是
"码明明是对的但提示无效" —— 玩家从聊天窗口复制码时带上空格、
大小写混乱是常态。

**客户端刻意不做格式校验**（只 `Trim`）：多拦一道只会让问题更难查。

### 字符集去掉了易混字符

码用 `ACDEFGHJKMNPQRTUVWXY34679`（24 个字符），**刻意去掉**
`0/O、1/I/L、2/Z、5/S、8/B`。

邀请码是**人工抄写/口述**的（发群里、念给朋友），混字符会让
"码是对的但抄错了"成为主要问题。

展示形式是 `XXXX-XXXX`（带连字符便于核对），存储与比对一律用归一化形式。

### 后台页面

后台 8443 → 左侧「账号管理」→ **邀请码**：

| 功能 | 说明 |
|---|---|
| 生成 | 数量（1–500）+ 有效期（小时，0=永久）+ 备注 |
| 导出全部可用码 | 下载 `.txt`（一行一个，带连字符）**并同时复制到剪贴板** |
| 列表 | 按状态筛选（未用/已用/过期/已作废）+ 搜码/备注/使用者账号 |
| 点码复制 | 表格里的码点击即复制 |
| 作废 | 只作废**未使用**的码（已用的作废会让追溯记录含混） |

生成接口的 `created_by` 存的是 AuthKey 的 **SHA-256 前 8 位**，不是明文 ——
AuthKey 等于后台密码，写进库里等于把密钥落盘。测试 `TestAdminActorHidesKey` 锁死这条。

### API

```bash
# 生成（需 X-Auth-Key）
curl -X POST http://127.0.0.1:8443/api/admin/invite/generate \
  -H "X-Auth-Key: <AuthKey>" -H "Content-Type: application/json" \
  -d '{"count":10,"note":"十月批次","expires_in_hours":720}'
# → {"ok":true,"codes":["K7M2-P9QX",...],"count":10,"expires_at":...}

# 列表（支持 ?status=unused|used|expired|disabled&keyword=&page=&page_size=）
curl -s "http://127.0.0.1:8443/api/admin/invite/list?status=unused" \
  -H "X-Auth-Key: <AuthKey>"

# 作废
curl -X POST http://127.0.0.1:8443/api/admin/invite/revoke \
  -H "X-Auth-Key: <AuthKey>" -d '{"code":"K7M2-P9QX"}'

# 导出（text/plain，触发下载）
curl -s "http://127.0.0.1:8443/api/admin/invite/export" \
  -H "X-Auth-Key: <AuthKey>"
```

### ⚠️ 升级影响（重要）

`Register.RequireInvite` **默认开启**。所以升级后如果后台一个码都没有，
**没人能注册**。

这是刻意的：这个开关的目的就是卡死注册入口。默认 false 等于
"配了但没生效"，运营以为开了、实际谁都能注册 ——
那种静默失效比"注册不了"危险得多。

**升级步骤**：先在后台生成一批邀请码，再放玩家进来。
需要临时放开就显式配 `"RequireInvite": false`。

### 关闭邀请码（回滚）

```json
"Register": { "RequireInvite": false }
```

关闭后回到改造前的自由注册（IP/机器限额仍然生效）。
注意：关闭前生成的码不会丢，重新开启后仍可用（只要没过期、没被作废）。

#### 老登录器兼容

老版本登录器只发 MD5、不发明文。此时：
- 平台账号照建（能登 S4A21/S5A95）
- S5A3 侧建不了 → 日志记 `注册未转发 S5A3（登录器未上报明文密码…）`
- 注册**仍然返回成功**（不因为 S5A3 建不了而让玩家什么都得不到）

#### 失败方向

| 情况 | 行为 |
|---|---|
| 平台账号建失败（限额/重名/库错） | 返回失败，玩家什么都得不到 |
| 平台账号建成、S5A3 转发失败 | **返回成功**，文案点名没建成的服（`注册成功（s5a3 服建号未完成，请稍后在该服重试或联系管理员）`） |
| 平台账号建成、老登录器无明文 | 返回成功（S5A3 侧需运营补建） |

> 原则：能用的部分先给玩家。平台账号是有用的（S4A21/S5A95 立刻能登），
> 不因为 S5A3 这一个服失败就整体回滚。

## 六、回滚

四处开关，任一处关掉即回退到对应行为：

| 开关 | 效果 |
|---|---|
| `Signing.PrivateKeyPath` 置空 | 清单不签名，登录器降级到 TLS pin |
| `Signing.PeerInternalUrl` 置空 | 关闭网关间同步 + 关闭登录反查（行为与单网关部署完全一致） |
| `Register.PlatformOnly` 配 false | 注册回到改造前行为（按 game 分流到 S5A3，不建平台账号） |
| `Register.RequireInvite` 配 false | 关闭邀请码（回到自由注册 + IP/机器限额） |
| `GameServerEntry.ListCaps` 不配（nil） | 门禁回到协议默认值（与改造前完全一致） |
| 登录器 `BuildDefaults.SigningPublicKey` 置空 | 不校验签名（但仍会拉清单） |

**登录器侧完全回滚**：删掉 `launcher-servers.dat` + 用改造前的 exe。
因为 `HttpBaseUrl` 在 `ActiveServerEntry == null` 时回退到编译期端点，
老配置的行为逐字节不变。

**只回滚同步、保留选服/签名**：把 `Signing.PeerInternalUrl` 置空即可 ——
选服、端点按服化、门禁 caps 全部照常工作，只是不再跨网关同步。
