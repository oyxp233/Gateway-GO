## 0. 一分钟版

```bash
# ── 改代码 ──────────────────────────────────────────
cd E:/DNF-Server/Gateway-GO     && git checkout feature/s5a3-standalone
cd E:/DNF-Server/Launcher-WPF   && git checkout s5a3

# ── 构建 ────────────────────────────────────────────
cd E:/DNF-Server/Gateway-GO   && sh build.sh            # → dist/linux-amd64/
cd E:/DNF-Server/Launcher-WPF && cmd //c build-s5a3-vm.bat   # VM 测试版
cd E:/DNF-Server/Launcher-WPF && cmd //c build-release.bat   # 生产版（按目标选脚本）

# ── 发版（顺序不能反）──────────────────────────────
# 1) 先网关：传二进制 + 重启（玩家掉线 ~10s，低峰做）
# 2) 再登录器：走 admin API 上传，禁止 scp 覆盖
curl -sk -X POST https://<网关>:8443/api/admin/launcher/upload \
     -H "X-Auth-Key: $KEY" \
     -F "file=@SimpleLauncher.exe" -F "version=2.7.3" -F "name=<变更说明>"

# ── 验证（必做）─────────────────────────────────────
curl -sk https://<网关>:8080/api/launcher/update        # version/hash 是否已变
curl -sk -o /dev/null -w '%{http_code}\n' \
     "https://<网关>:8080/api/launcher/update/delta?from=<旧hash>"   # 必须 200，不能 404
```

## 3. ★★★ 更新文件只能走管理 API（事故复盘）

### 3.1 事故现象

发新版登录器后，大量玩家不是下几百 KB 的增量，而是**全量重下 130 MB**，
把 12 MB/s 的上行打满，正在游戏里的玩家卡顿。

### 3.2 根因

有人**没有走管理 API**，直接把新 exe 拷到服务器覆盖了：

```bash
# ❌ 错误做法
scp SimpleLauncher.exe root@server:/opt/s5a3/gateway/launcher_update/current.exe
```

网关会按 `size + mtime` 感知新文件、清单也会变，**看起来一切正常** ——
所以问题很隐蔽。但：

```
直接覆盖 current.exe
  → history/index.json 里没有这个新版本的记录
  → 客户端拿本地旧 hash 请求 delta?from=<旧hash>
  → 网关在 history 里找不到 → 404
  → 客户端按设计回退「全量下载」
  → 130 MB × N 人 → 上行打满 → 游戏卡顿
```

同理适用于 `dnfexe_update/current.exe` 和 `plugins/` 下的文件。

### 3.3 正确做法

| 通道 | 唯一正确入口 |
|---|---|
| 登录器自更新 | `POST /api/admin/launcher/upload`（multipart：`file` + `version` + `name`） |
| DNF.exe | `POST /api/admin/dnfexe/upload`（同上） |
| PVF | `POST /api/admin/upload-pvf`（multipart：`file` + `name`） |
| 插件 | `POST /api/admin/plugins/upload`（multipart：`file`，文件名即插件名） |

这些接口会做**四件事**，少一件就会退化成全量：

1. 落盘 `current.*`
2. **复制进 `history/<HASH>.exe`**
3. **追加 `history/index.json`**
4. 触发 PeerSync 同步给从网关

### 3.4 上传后必须验证

```bash
# 1) 清单已经是新版本
curl -sk https://127.0.0.1:8080/api/launcher/update
# 期望：version=新版本，hash=新 hash

# 2) 旧版本能拿到增量（这一步最关键）
curl -sk -o /dev/null -w '%{http_code}\n' \
  "https://127.0.0.1:8080/api/launcher/update/delta?from=<上一个版本的hash>"
# 期望：200。如果是 404，说明 history 缺失 —— 立即停下，别让玩家升级
```

DNF.exe 把 URL 换成 `/api/dnfexe/update/delta?from=...`；PVF 换成
`/api/launcher/pvf/delta?from=...`。

> DNF.exe / 登录器的按需增量是**请求时现场生成并缓存**的，第一次 200 后
> `delta/` 目录下会出现缓存文件。生成 130 MB 的差分需要几秒，属正常。

## 4. 发版顺序

```
① 网关变更（如有）
     └─ 备份旧二进制 → 传新二进制 + wwwroot → restart → 验证端口/日志
② 登录器变更
     └─ 构建目标版本 → 先自测（VM）→ admin API 上传 → 验证 delta 200 → 观察更新高峰
```

**为什么先网关后登录器**：新版登录器通常依赖网关的新接口/新字段。
先发登录器会出现「客户端请求了新端点、网关 404」，玩家卡在更新检查。

**为什么都放低峰**：

- 重启 `s5a3-gateway` ⇒ 全体玩家掉线（约 10 s）
- 上传新登录器 ⇒ 所有玩家下次启动都会检查更新

## 5. 构建

### 5.1 网关

```bash
cd E:/DNF-Server/Gateway-GO
sh build.sh                 # 默认 linux/amd64 → dist/linux-amd64/
```

产物三件：`s5a3-gateway`、`s5a3-admin`、`wwwroot/`。

> ★ `wwwroot` 是后台页面，**从磁盘读，不走 go:embed**。
> 只传二进制不传 `wwwroot` ⇒ 后台还是旧页面。

### 5.2 登录器

编译目标由 `DefineConstants` 决定，**每个目标对应一套网关地址与证书 pin**：

| 脚本 | 目标 | 说明 |
|---|---|---|
| `build-s5a3-vm.bat` | `TEST_S5A3_VM` | 测试 VM（192.168.215.128），发布后校验内嵌地址，不符即删产物 |
| `build-s5a3-90cn.bat` | `TEST_S5A3_90CN` | 90CN |
| `build-s5a3-216.bat` | `TEST_S5A3_216` | 216 |
| `build-release.bat` | 空（生产） | 正式服 |

> ★ 版本号有**两处**：`LauncherConfig.LauncherVersion` 与 `csproj <Version>`，
> 必须一起改。只改一处会出现「界面显示新版、网关仍按旧版放行/拦截」。
> 新增构建目标时，还要把常量名加进 `csproj` 的 `ValidateBuildTarget` 白名单。

## 6. 部署

### 6.1 网关

```bash
TS=$(date +%Y%m%d-%H%M%S)
cp -a /opt/s5a3/gateway/s5a3-gateway /opt/s5a3/gateway/backups/s5a3-gateway.bak-$TS
install -m 755 /tmp/s5a3-gateway.new /opt/s5a3/gateway/s5a3-gateway
# admin 有改动时同样替换 s5a3-admin；wwwroot 用 rsync/cp -a 覆盖
systemctl restart s5a3-gateway
systemctl is-active s5a3-gateway
journalctl -u s5a3-gateway -n 30 --no-pager
```

> ★ `install` 会换 inode。**只传文件不重启 = 进程还在跑旧代码**，
> 而 `sha256sum` 全绿会骗人。判「真换」看 `systemctl show -p MainPID --value` 是否变。

### 6.2 登录器

不要手动拷，走 §3.3 的 API。上传后按 §3.4 验证。

## 7. 下载限速参数

四条下载通道共用闸门（2026-11-16 上线）：

| 变量 | 默认 | 说明 |
|---|---|---|
| `S5A3_DL_RATE_MBPS` | 8 | 全局总出口；`0` = 关闭限速与并发闸门 |
| `S5A3_DL_PER_IP_MBPS` | 2 | 单 IP 上限；`0` = 不限 |
| `S5A3_DL_CONCURRENCY` | 8 | 并发下载路数 |
| `S5A3_DL_GATE_WAIT_SECONDS` | 45 | 排队等待上限，超时才 503 |

- 写在 `gateway.env` 或 systemd drop-in，改完 `restart` 生效。
- 做对照实验时用 drop-in，**测完删掉**，别忘了 `daemon-reload` + `restart`。
- 验速率至少跑 20~30 秒：10 秒会把 TLS 建连/首字节开销摊进去，读数偏低
  （2026-11-16 实测 10 s 显示 1.25 MB/s，30 s 才是真实 2.0 MB/s）。

## 8. 回滚

| 对象 | 操作 |
|---|---|
| 网关二进制 | `install -m755 backups/s5a3-gateway.bak-<TS> /opt/s5a3/gateway/s5a3-gateway && systemctl restart s5a3-gateway` |
| 登录器 | `POST /api/admin/launcher/rollback`，body `{"hash":"<历史hash>"}` |
| DNF.exe | `POST /api/admin/dnfexe/rollback`，同上 |
| PVF | `POST /api/admin/pvf/rollback`，同上 |
| 插件下发 | 后台关「插件下发」开关（`enabled=false`），客户端退回内置插件 |
| 下载限速 | `S5A3_DL_RATE_MBPS=0` 后重启 |

## 9. 故障排查

| 现象 | 先查什么 | 常见原因 |
|---|---|---|
| 玩家更新时全量下载 130 MB | `delta?from=<hash>` 返回码 | history 缺记录（手拷覆盖）／客户端 exe 被改过 hash 对不上 |
| 更新完仍提示要更新 | 清单 `hash` 与本地 exe 实际 sha256 | 传错文件／CDN/中间层缓存 |
| 后台页面是新功能、网关行为是旧的 | 两个进程的二进制时间与 sha | 只换了 admin 没换 gateway，或换了没重启 |
| 上传成功但玩家拿不到新版本 | `launcher_update/current.exe` 的 mtime/size | 网关没权限读／PeerSync 从网关未同步 |
| 大批玩家 503 | 网关日志 + 并发闸门 | 并发 8 已满且排队超 45 s；调 `S5A3_DL_CONCURRENCY` |
| 下载速度明显低于设定 | 测量时长、TLS、客户端上限 | 短测误差；客户端 `S5A3_LAUNCHER_DL_KBPS` 更低 |
| 登录器提示「反外挂插件未能接入」 | AC 命名管道、`AC-S5A3.dll` 是否在核心插件里 | 插件未部署／管道被拦／不是 S5A3 目标构建 |
